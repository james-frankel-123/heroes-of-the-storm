In-Game Draft Companion
Native Windows Overlay

A native Windows app that overlays a running Heroes of the Storm client and gives live pick and ban recommendations from our on-device draft engine. Draft state comes from reliable sources — your own quick taps plus optional screen auto-fill — while real battletags and the final draft are read straight from the game's own files. No fragile screen-reading in the critical path.

Overview

The companion runs on the player's machine and stays passive: it reads the screen (optionally) and parses files the game already writes to disk. It never injects into or reads the memory of the game process. Heavy work happens on the client; our existing Vercel + Neon backend keeps its current role. It duplicates the website's draft engine — same recommendations — where you actually draft.

Client — native C# / WinUI 3

  • Transparent, click-through, always-on-top overlay
  • Live draft input: quick manual taps + optional screen auto-fill (heroes + map)
  • On-device recommendations via ONNX Runtime — picks and bans
  • Reads the game's own replay.server.battlelobby and .StormReplay files

Backend — existing Vercel + Neon

  • Neon Postgres: accounts, community stats, synced replay data
  • Community + personal stat lookups that feed recommendations
  • New ingest route to receive synced replay data from the client

Why the engine runs on-device

Today the draft search already runs client-side (ONNX Runtime Web in browser workers), so moving it to a serverless function would add cold starts, bundle-size friction, and a network round-trip inside a ~30–45s draft window. Running the models natively on the client keeps recommendations instant and offline; the backend stays lean and does only what it already does well.

Game-State Sources

A verified feasibility spike settled the question that shapes this whole design: what game state can we get without fragile screen-reading, and when? The answer drives everything below.

Finding

Battletags (with the #1234 discriminator), the authoritative final draft, and match history all come CV-free from the game's own files. But no file exposes live mid-draft state — the lobby file is written only at the loading screen, after the draft. So live picks/bans come from the player's taps (always) plus optional screen auto-fill; the file then reconciles everything at match load.

What the spike verified

Adversarially fact-checked against production open-source parsers (HeroesToolChest, barrett777/Heroes.ReplayParser, hotsapi/HotsStats):

  • The game writes %LOCALAPPDATA%\Temp\Heroes of the Storm\TempWriteReplayP1\replay.server.battlelobby, containing full battletags with discriminators plus the final picks, bans, and map — the discriminator the draft UI hides is right there in plaintext.
  • Timing (decisive): that file is created "at the start of the loading screen," i.e. after the draft completes. No disk, API, rich-presence, or log source exposes picks/bans as they happen mid-draft. That's why live capture cannot be file-only.
  • ToS: reading these on-disk files is de-facto tolerated (Blizzard's Warden scans process memory, not disk); we never read memory. Note: there is no explicit Blizzard blessing — tolerance is inferred from years of tools operating openly.
✓ Verified hands-on — 2026-07-17, game build 97039. A ranked Storm League draft on a current-patch Windows + HotS box confirmed all four points: (1) the file appears only at loading-screen start — nothing during the draft; (2) current-patch #1234 discriminator extraction works; (3) it's written fully-formed and stable, so a copy is safe to read immediately; (4) bans + picks + map are all present for Storm League. Full results in Getting Started. The format is still undocumented and shifts across game builds, so it keeps a per-patch maintenance tail.

1 Overlay & Live Draft Input

A transparent surface over the game that both captures the live draft and draws recommendations — without stealing focus or clicks.

Decision

Build the overlay as a WinUI 3 layered, always-on-top, click-through window (Win32 ex-styles WS_EX_LAYERED / TRANSPARENT / TOPMOST / NOACTIVATE via P/Invoke; HotS in borderless windowed mode). Capture live draft state two ways, built together: a reliable manual/click baseline, plus an optional screen auto-fill layer on top. Battletags are never read from the screen — they come from the lobby file.

The two input paths

Manual / click entry — baseline

  • Tap each hero as it's picked or banned, from a hero grid in the overlay (the model your website already uses).
  • Fully CV-free and deterministic — the feature always works, on any resolution, patch, or client language.

Screen auto-fill — optional layer

  • Detects hero portraits + map and pre-fills your taps, so you confirm instead of type.
  • Every auto-fill is a suggestion you can override; on low confidence it just falls back to manual. Never a single point of failure.

Voice input — planned third path

Planned

Let the player just say what's on screen — "they banned Muradin", "enemy picked Jaina", "map is Sky Temple" — and have the overlay update. Recognition runs against a closed vocabulary (the 90 heroes and 14 maps we already ship) rather than open dictation, which is what makes this tractable: the recognizer is choosing among known words, not transcribing English.

Why it earns a place: during a draft your hands are on the hero pool and the clock is short, so the expensive interaction isn't entering a pick — it's correcting one the auto-fill got wrong. Speaking a correction costs no clicks and no alt-tab. It's also the natural fallback on any machine where screen capture is unavailable or mis-calibrated.

  • Push-to-talk, not hot mic. A hotkey gates the recognizer so we never capture team voice comms or ambient room audio, and so the feature can't fire on someone else's call.
  • On-device recognition preferred — no per-utterance network hop inside the draft window, no audio leaving the machine, no added cost per draft. A cloud recognizer is the fallback if local accuracy on hero names proves poor.
  • Intent, not transcript. Utterances map onto the same small set of actions the taps already produce: ban / our pick / enemy pick / map / undo.
  • Known risk — homophones. Hero names collide with each other and with common speech ("Mei"/"May", "Chen"/"Zen", "Cho"/"Gall" as one pick). Ambiguous matches must ask for confirmation rather than silently choosing, on the same principle as a low-confidence auto-fill.

Overlay technology — alternatives considered

OptionWhy
WinUI 3 overlay windowChosenModern native stack: DPI/HDR-aware composition, good performance, full access to the Win32 ex-styles for click-through + topmost. Shares one process/toolchain with the native engine and capture.
DirectX hook / DLL injection (Discord/Steam style)RejectedThe only way to draw over true exclusive-fullscreen DirectX, but it injects into the game process — an anti-cheat / ToS risk that breaks our passive-only principle.
WPF / WinForms transparent windowRejectedWorks, but it's the legacy stack — weaker composition/DPI/HDR than WinUI 3, with no offsetting benefit for a new build.
Electron transparent BrowserWindowRejectedMax web-code reuse, but a heavy runtime for a Windows-only app; native C# keeps overlay, capture, and inference in one process.
Constraint to surface to users: exclusive-fullscreen HotS cannot be overlaid without injection. We require/recommend borderless windowed mode and detect + prompt if the user is in exclusive fullscreen.

Key risks

  • Correct z-ordering against a fullscreen DirectX app; staying topmost without stealing focus.
  • Multi-monitor and mixed-DPI setups; positioning the panel and any ROIs relative to the game window, not the desktop.

2 Screen Auto-Fill (Heroes + Map)

An optional assist that pre-fills the draft so the user confirms instead of types. Deliberately scoped and never load-bearing.

Decision

When enabled, capture the game window with the Windows Graphics Capture API, crop regions of interest, and identify hero portraits (OpenCV template matching via OpenCvSharp) and the map. That's the whole CV surface — no battletag OCR (the discriminator isn't on screen; the lobby file has it). Auto-fills are confirmable suggestions, and the lobby file overrides them at match load.

Capture method

OptionWhy
Windows Graphics Capture (WGC)ChosenModern, supported, GPU-friendly, and can target the game window specifically. The same API OBS uses for game capture.
Desktop Duplication (DXGI)FallbackFast and reliable but monitor-level and more complex. A backup if WGC misbehaves on a given GPU/driver.
GDI BitBlt / PrintWindowRejectedSimplest, but slow and frequently returns black frames from hardware-accelerated surfaces.

Recognition method

Template match on portraits + map readChosenOffline, deterministic, low-latency. Portraits are distinct art matched against our 90-hero asset library; results are validated against the model's canonical roster.
Multimodal LLM visionFallbackFlexible tie-breaker for a genuinely ambiguous frame, but per-frame cost/latency and sends screenshots off-device. Not in the default path.
Read game memory / logs for live stateRejectedThe spike confirmed no disk/API/log source exposes live mid-draft state, and memory reading trips Warden. So live capture is taps + optional CV; the file supplies the rest at load.
What actually happened — both decisions above were reversed. Recorded here rather than quietly edited, because the reasons are the useful part.
  • Capture: WGC lost to the "rejected" option. On Windows 10, Graphics Capture forces a yellow capture border that flashed through every draft, and it froze the game during play. Win10 has no API to suppress it. PrintWindow(PW_RENDERFULLCONTENT) — rejected above as slow and black-frame-prone — captures the DirectX draft screen at full fidelity with no border, and is what ships.
  • Recognition: template matching is dead; vision LLM is the default path. Hero-name OCR failed outright (names render as light-blue italic text on a light-blue banner — same hue, and no threshold separates them). Portrait correlation ranked the wrong hero even on a clean crop, and hero skins would have broken it regardless. A vision model reads the screen instead — robust to skins, resolution, and UI drift.
  • The real lesson was about framing, not models. The vision model kept reporting heroes nobody picked and putting enemy heroes on our team. The cause wasn't the model: we were sending the entire ultrawide frame, in which the two team columns are thin strips at the far edges (~12% of width each) while a hero splash dominates the middle and renders the previewing hero's name in the largest text on screen. Sending labelled crops of just the columns, bans, and map made team identity structural — decided by which region we cut, not by the model's judgement — and the errors stopped.

Honest about the hard parts

The draft screen is not a fixed layout — different aspect ratios reposition elements and Blizzard shifts the UI subtly between patches. That's exactly why auto-fill is an assistive layer with a manual fallback, not the source of truth. ROI coordinates + portrait assets ship as versioned config, updatable without a client release.

Key risks

  • Aspect-ratio & patch drift — the reason CV is optional and always correctable, and why manual entry is the baseline.
  • Confidence thresholds tuned so a shaky frame degrades to "tap to confirm," never a wrong silent pick.
  • Localized clients change map text — prefer portrait matching over text where possible.

3 On-Device Engine

Run the recommendation models and search locally — for both picks and bans — with zero round-trips during the draft. Same engine as the website.

Decision

Load the existing ONNX models (draft_policy.onnx, generic_draft_0.onnx, win_probability.onnx) with Microsoft.ML.OnnxRuntime in C#, and port the neural MCTS orchestration from src/lib/draft to C#. It recommends across the full sequence — 10 picks and 6 bans. Hero/map/tier encodings are copied verbatim from ai-inference.ts — the contract with the trained models. Scope note: the old greedy/statistical pipeline is retired on the web, so the port targets the neural MCTS path only.

Alternatives considered

OptionWhy
Native C# ONNX Runtime + ported searchChosenInstant, offline, no per-pick network hop; the .onnx files are portable and .NET has first-class ONNX Runtime support. Cost: reimplementing the search in C# and keeping encodings in sync.
New Vercel API endpoint (onnxruntime-node)RejectedLarge native binaries fight serverless bundle limits, functions have execution-time caps, and cold starts + a network hop hurt inside a live draft.
Dedicated Node service (Fly / Railway / Render)FallbackReuses the TS engine on a persistent container with no Lambda limits, but adds infra + cost and still a network hop. The fallback if the C# port proves too costly.
Embed onnxruntime-web in a WebView2RejectedReuses the browser path, but re-introduces a JS runtime and defeats the point of going native.

Key risks & how we verify

  • Encoding parity (Layer 1): generate the hero/map lists from one shared source so the C# client and training never drift; the input tensors must be byte-identical to the web engine.
  • Numerical parity — within margin, not bit-exact: onnxruntime-web and Microsoft.ML.OnnxRuntime differ slightly in float32, and the search samples the opponent with Math.random() — so exact equality is neither achievable nor needed. We verify in layers: single-model forward passes must agree within a slim tolerance; the full MCTS is checked in a deterministic test mode (a shared mock RNG both sides step through, plus an uncapped time budget / fixed sim count), and in the wild by statistical agreement of recommendations.
  • Parity oracle: a saved answer-key of input→output pairs for the model calculations, plus the live web engine (headless browser) as the source of truth for the random tree search — less brittle than hand-exported fixtures.
  • Responsiveness: run search off the UI thread so the overlay never stalls; in production the search keeps the web engine's wall-clock budget (the uncapped mode is test-only).
  • Model versioning & updates: pin model + encoding versions together so a model swap can't silently break inputs; the client checks for and downloads new model versions on demand rather than bundling them permanently.

Backend & Replay Sync

How the client and our existing backend exchange data, and how personal stats stay current.

Replay sync

  • On first run the client scans Documents\Heroes of the Storm\Accounts\…\Replays\Multiplayer\ and parses .StormReplay files with the Heroes.ReplayParser .NET library — and keeps syncing regularly during use, not just once.
  • Replay data syncs off the machine to the backend (this is intended — it's how a player's stats stay current across sessions and devices, and how community aggregates grow).
  • A new ingest API route receives the synced replay data into Neon.

What "community + personal stats" means

  • Community stats — aggregate hero / map / pairwise win rates, bucketed by rank tier (low / mid / high), that feed the baseline recommendation.
  • Personal stats — the player's own synced history (e.g. the momentum-adjusted win % the site already specifies), which personalizes the recommendation for heroes they actually play well.
  • At the loading screen, the client reads replay.server.battlelobby for the real battletags + final draft — reconciling any manual/CV entry and letting personalization key off everyone in the lobby, not just the local player.

No LLM "why this pick" explanations for now — the ones we've tried have been detractive. The app matches in-browser behaviour instead.

Fast-follows (post-beta)

  • Recognition robustness — the region crops that auto-fill depends on are calibrated against a 3440×1440 ultrawide and carry an automatic full-frame fallback, but 16:9 is still unverified. Localized clients remain untested.
  • Patch resilience — ROI + battlelobby config that updates without a client release. The lobby format shifts per game build, so this has a standing maintenance tail.
  • Model updates on demand — models ship bundled today; the client should fetch new versions rather than requiring a reinstall.
  • Overlay polish — collapse-to-pill between picks, multi-anchor layouts, per-user placement.
Ship-early note: because the manual baseline (M2) delivers live pick/ban advice with zero CV, we have a usable product well before the auto-fill layer (M4) exists. CV is added on top only once M0 proves the file half and the baseline is solid.

What the real draft screen tells us

The live screen (above) shapes both the overlay and the optional auto-fill layer:

  • Teams are vertical hex columns — yours (blue) down the left edge, the enemy (red) down the right — not horizontal rows. So the overlay tucks into the dark band beside the centre pick-splash and must never cover either column or the bottom hero pool.
  • Little empty space. The screen is dense, so the overlay stays compact and corner-anchored (collapsing to a pill between picks) rather than a large panel.
  • What auto-fill reads: hero portraits (the hex slots + bottom pool) and the map name — the distinct visual targets. Battletags are NOT read from the screen — the draft UI hides the #1234 discriminator, so those come from the lobby file at load.
  • Caveat: this is a Custom / vs-A.I. lobby (note "Elite A.I." and no ban phase). Ranked Storm League draft adds a ban row and pick-order/timer UI, so we calibrate against a real Storm League draft — not this screen.

Getting Started — M0

The first hands-on step, to run on a Windows PC that has Heroes of the Storm installed. It confirms the CV-free half of the design before we build on it. Plan to play (or spectate) one ranked Storm League draft — that's the exact surface we care about. No coding required.

✓ Verified 2026-07-17 — all four checks passed (game build 97039). A ranked Storm League draft on a current-patch box confirmed the file-based half end-to-end:
  • ✓ Check 1 (timing) — nothing written during queue or the ban/pick draft; the battlelobby appeared only at the loading screen.
  • ✓ Check 3 (safe-to-read) — written fully-formed (≈282 KB) and never changed size after; safe to copy immediately.
  • ✓ Check 2 (battletags) — all 10 players decoded with full Name#1234 discriminators (incl. spec battletag Mestupidum#1183).
  • ✓ Check 4 (completeness) — Game Mode StormLeague, 6 bans (ThreeBan), 10 picks, map, and team assignments all present.

New findings — carry into M3 (file integration)

  • Stale temp file gotcha. The battlelobby persists in …\TempWriteReplayP1\ after a match — a leftover from a prior game was already present before the test. "File exists" is not proof of the current draft; the client must detect a fresh write (a new LastWriteTime/size), or clear/baseline the path before the match, not just check for presence.
  • Pregame pick format differs from post-match. In the battlelobby, picks come as 4-char attribute IDs (Witc, Diab, Garr…), not the HeroWitchDoctor-style names a finished .StormReplay gives. The client needs an AttId → canonical-roster map to line these up with the model's hero list.
  • Tooling reality. HeroesDecode 1.4.x requires .NET 8 (won't install on .NET 5) and uses HeroesDecode pregame -p <file> (a subcommand, not a flag). The user-local .NET installer avoids an elevation hang seen with the winget MSI. The steps below are corrected accordingly.

Reproducible procedure (re-run after future patches)

1One-time setup

HeroesDecode needs .NET 8+. Install the SDK with the user-local installer (no admin — avoids the winget MSI elevation hang), then install HeroesDecode — the community CLI that reads the lobby file:

# .NET 8 SDK, user-local (no admin needed):
$s = "$env:TEMP\dotnet-install.ps1"
irm https://dot.net/v1/dotnet-install.ps1 -OutFile $s
& $s -Channel 8.0 -InstallDir "$env:LOCALAPPDATA\Microsoft\dotnet"
$env:DOTNET_ROOT = "$env:LOCALAPPDATA\Microsoft\dotnet"
$env:Path = "$env:DOTNET_ROOT;$env:USERPROFILE\.dotnet\tools;$env:Path"

# HeroesDecode (needs .NET 8):
dotnet tool install --global HeroesDecode
HeroesDecode --help   # note: 'pregame' is a SUBCOMMAND, not a flag

2Check 1 & 3 — timing & safe-to-read

Before you queue, open PowerShell and start this watcher. It prints a timestamped line whenever the lobby file exists and how big it is:

$dir = "$env:LOCALAPPDATA\Temp\Heroes of the Storm"
while ($true) {
  Get-ChildItem $dir -Recurse -Filter replay.server.battlelobby -ErrorAction SilentlyContinue |
    ForEach-Object { "{0:HH:mm:ss.fff}  {1} bytes" -f (Get-Date), $_.Length }
  Start-Sleep -Milliseconds 500
}

Now play. Watch the console: during the ban/pick draft you should see nothing (confirms no live file — Check 1); at the loading screen note when it first appears and when the byte-size stops changing (the safe-to-read moment — Check 3). Don't open the original with a write lock while the game holds it — that has crashed other tools.

Gotcha (confirmed on the 2026-07-17 run): a battlelobby from a previous match can still be sitting in that folder. Before you queue, delete or rename any existing replay.server.battlelobby so the fresh write at the loading screen is unambiguous — otherwise the stale file masks Check 1.

3Check 2 & 4 — contents

When the file appears at loading, copy it first (never parse the live original), then decode the copy. In HeroesDecode 1.4.x, pregame is a subcommand with a required -p path:

$src = (Get-ChildItem "$env:LOCALAPPDATA\Temp\Heroes of the Storm" -Recurse -Filter replay.server.battlelobby | Select-Object -First 1).FullName
Copy-Item $src "$env:TEMP\bl_copy.battlelobby"
HeroesDecode pregame -p "$env:TEMP\bl_copy.battlelobby"   # or: get-pregame-json -p <file> for JSON

4What "pass" looks like

  • ✓ Nothing written during the draft; the file appears at loading-screen start.
  • ✓ Decode shows all 10 players with full Name#1234 battletags.
  • ✓ Decode shows the 6 bans, 10 picks, the map, and team assignments.
  • ✓ The game was a ranked Storm League match (not QM / Custom).

What the results mean

  • All pass → the architecture holds: CV is needed only for the live moment, the file is authoritative at load.
  • File appears earlier / during draft → good news — it could shrink the CV role. Note when it appears and flag it.
  • Missing discriminator or bans on this patch → the parser needs a per-build fix; note the game build number.
