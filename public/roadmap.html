HotS Fever · Product Roadmap

In-Game Draft Companion
Native Windows Overlay

A native Windows app that overlays a running Heroes of the Storm client, reads the live draft off the screen, and recommends the next pick using our on-device draft engine — with optional LLM explanations.

Overview 1 · Overlay Window 2 · Screen Vision 3 · On-Device Engine Backend & Data Phasing MVP & Timeline Mockups

Overview

The companion runs entirely on the player's machine and stays passive: it only reads the screen and parses replay files Blizzard already writes to disk. It never injects into or interacts with the game process. Heavy work happens on the client; our existing Vercel + Neon backend keeps its current role.

Client — native C# / WinUI 3

  • Transparent, click-through, always-on-top overlay
  • Screen capture → computer vision → live draft state
  • Draft search runs on-device via ONNX Runtime
  • Parses local .StormReplay files on first run

Backend — existing Vercel + Neon

  • Neon Postgres: accounts, community stats, imported match summaries
  • /api/gameplan: optional LLM "why this pick" explanations
  • Community / personal stat lookups
  • New ingest route for parsed replay summaries (raw replays never leave the machine)

Why this split

Today the draft search already runs client-side (ONNX Runtime Web in browser workers), so moving it to a serverless function would add cold starts, bundle-size friction, and a network round-trip inside a ~30–45s draft window. Running the models natively on the client keeps recommendations instant and offline; the backend stays lean and does only what it already does well.

1 The Overlay Window

A transparent surface layered over the game that draws recommendations without stealing focus or clicks.

Decision

Build the overlay as a WinUI 3 (Windows App SDK) layered, always-on-top window, made click-through and non-activating via Win32 extended window styles (WS_EX_LAYERED, WS_EX_TRANSPARENT, WS_EX_TOPMOST, WS_EX_NOACTIVATE) applied through P/Invoke. HotS must run in borderless / windowed-fullscreen mode so a separate window can composite on top.

Alternatives considered

OptionWhy
WinUI 3 overlay window Chosen Modern native Windows stack: DPI/HDR-aware composition, good performance, and full access to the Win32 ex-styles we need for click-through + topmost. Pairs cleanly with the native ONNX and capture work.
DirectX hook / DLL injection (Discord/Steam/RTSS style) Rejected The only way to draw over true exclusive-fullscreen DirectX, but it injects into the game process — an anti-cheat / ToS risk that breaks our passive-only principle.
WPF / WinForms transparent window Rejected Would work, but it's the legacy stack — weaker composition, DPI, and HDR story than WinUI 3, with no offsetting benefit for a new build.
Electron transparent BrowserWindow Rejected Max web-code reuse, but a heavy runtime for a Windows-only app, and we chose native C# so overlay, capture, and inference share one process and toolchain.
Constraint to surface to users: exclusive-fullscreen HotS cannot be overlaid by a separate window without injection. We require/recommend borderless windowed mode and detect+prompt if the user is in exclusive fullscreen.

Key risks

  • Correct z-ordering against a fullscreen DirectX app; keeping the overlay topmost without stealing focus.
  • Multi-monitor and mixed-DPI setups; positioning ROIs relative to the game window, not the desktop.

2 Screen Vision → Draft State

Turn pixels into a structured draft: the 10 picks/bans, the map, and the 10 battletags.

Decision

Capture the game window with the Windows Graphics Capture API, crop fixed regions of interest (the draft UI is a known, fixed layout — normalized to resolution/aspect), then identify content with OpenCV template matching (OpenCvSharp) for hero portraits and the map banner, and Tesseract OCR for battletags. Detected heroes/maps are validated against our canonical 90-hero / 14-map roster before use.

Capture method

OptionWhy
Windows Graphics Capture (WGC)ChosenModern, supported, GPU-friendly, and can target a specific window (the game) rather than the whole desktop. This is the same API OBS uses for game capture.
Desktop Duplication (DXGI)FallbackFast and reliable but monitor-level (not window-scoped) and more complex. A viable backup if WGC misbehaves on a given GPU/driver.
GDI BitBlt / PrintWindowRejectedSimplest to write, but slow and frequently returns black frames from hardware-accelerated (DirectX) surfaces.

Recognition method

OptionWhy
Template match + OCR over fixed ROIsChosenOffline, deterministic, zero per-frame cost, and low latency. The draft screen's fixed layout lets us crop exact slots instead of searching whole frames, which makes matching cheap and reliable.
Multimodal LLM vision (screenshots → model)FallbackFlexible and quick to prototype, but per-frame cost + latency, needs connectivity every pick, and sends screenshots off-device. Reserved as a tie-breaker for low-confidence frames only.
Read game memory / log filesRejectedHotS exposes no supported live API; memory reading trips anti-cheat and violates our passive principle. There is no reliable live-state file during a match.

Why template match + OCR

The draft UI is fixed-layout, so we know where each portrait, the map banner, and each battletag render as ratios of the frame. Cropping those ROIs first makes recognition fast, cheap, and offline. Battletags follow a known Name#1234 format we can validate, and heroes/maps are checked against the same encodings the models were trained on (90 heroes sorted alphabetically, 14 maps).

Key risks

  • Patch UI drift: Blizzard moves/restyles the draft UI. Mitigation: version the ROI coordinates + portrait assets as config, updatable without a client release.
  • Resolution / aspect-ratio and UI-scale variation; confidence thresholds and a manual-correction fallback in the overlay.
  • Localized clients change map/hero text — prefer portrait matching over text where possible.

3 On-Device Engine & Search Port

Run the recommendation models and search locally, with zero round-trips during the draft.

Decision

Load the existing ONNX models (draft_policy.onnx, generic_draft_0.onnx, win_probability.onnx) with Microsoft.ML.OnnxRuntime in C#, and port the expectimax / MCTS orchestration from src/lib/draft (TypeScript) to C#. The hero/map/tier encodings are copied verbatim from ai-inference.ts — they are the contract with the trained models and must match training exactly.

Alternatives considered

OptionWhy
Native C# ONNX Runtime + ported searchChosenInstant, offline, no per-pick network hop; the .onnx files are already portable and .NET has first-class ONNX Runtime support. Cost: reimplementing the search in C# and keeping encodings in sync.
New Vercel API endpoint (onnxruntime-node)RejectedMax code reuse, but large native binaries fight serverless bundle limits, functions have execution-time caps, and cold starts + a network round-trip hurt inside a live draft.
Dedicated Node service (Fly / Railway / Render)FallbackReuses the TS engine on a persistent container with no Lambda limits, but adds infra + cost and still a network hop. The fallback if the C# port proves too costly.
Embed onnxruntime-web in a WebView2RejectedReuses the browser code path, but re-introduces a JS runtime and defeats the point of going native.

Why native C#

During a draft, latency is the product. A local engine returns a recommendation the instant a pick lands, works with no connectivity, and reuses the exact model artifacts we already ship. The tradeoff — porting the search — is bounded work we can verify directly against the current implementation.

Key risks & how we verify

  • Encoding parity: generate the hero/map lists from one shared source so the C# client and training never drift.
  • Numerical parity: golden test set — run N draft states through both the existing TS/browser path and the new C# path; assert policy/value agreement within tolerance and identical top recommendation.
  • Responsiveness: run search off the UI thread so the overlay never stalls.
  • Model versioning: pin model + encoding versions together so a model swap can't silently break inputs.

Backend & Replay Import

The one place the client talks to the network for data, plus the first-run import that makes personal insights work without setup.

  • Replay parsing is client-side. On first run we scan Documents\Heroes of the Storm\Accounts\…\Replays\Multiplayer\ and parse .StormReplay files with the mature Heroes.ReplayParser .NET library.
  • Only structured summaries are uploaded to Neon via a new ingest API route — never the raw replays. This powers personal stats (e.g. the momentum-adjusted win % already specified for the site).
  • LLM explanations reuse the existing streaming /api/gameplan route; the "why" text is optional and never blocks the recommendation.

Phasing

De-risk the two novel subsystems before building the live overlay. Ship one working slice at a time.

Slice 0
Vertical slice, no overlay: parse one local replay → upload a summary; and run the CV+OCR pipeline on a single captured screenshot → print the detected draft state. Proves replay import and vision independently.
Slice 1
Port the draft search to C# + native ONNX Runtime; validate against the TS engine with the golden test set.
Slice 2
Live capture loop → draft state → local recommendation, printed to a console (still no overlay).
Slice 3
The transparent WinUI overlay: render the recommendation in-game, with borderless-mode detection and manual correction.
Slice 4
Full first-run replay import + personal insights; optional LLM explanations via /api/gameplan.
Before shipping: a formal review of Blizzard's ToS / anti-cheat stance on passive screen-reading overlays. Our design stays read-only and injection-free specifically to stay on the safe side, but this must be confirmed, not assumed.

MVP & Timeline

The fastest path to a differentiated product in players' hands — a native overlay that reads the live Storm League draft and recommends the strongest next pick, offline.

≈ 7–8 weeks focused build to a shippable beta · ~2.5 months with real-world buffer · rough internal alpha in ~3 weeks

✓ In the MVP (v1)

  • Native WinUI overlay over Storm League draft, with borderless-mode detection
  • Screen vision: hero portraits, map, and bans — common resolutions (1080p/1440p, 16:9), English client
  • One-click correction on any low-confidence detection
  • Full on-device search (expectimax / MCTS + ONNX, ported to C#) — top pick + 2 alternatives + team win %
  • Community-tier stats (low / mid / high rank)

→ Deferred to fast-follows

  • Personalized recommendations (auto replay import + personal stats)
  • LLM "why this pick" explanations
  • Non-Storm-League screens, ultrawide / exotic resolutions, localized clients
  • Overlay polish (collapse-to-pill, multi-anchor layouts)

Why this scope ships fast

Two design choices keep the timeline tight without gutting the value: the one-click correction fallback means vision only has to be good, not perfect, to ship; and launching on community stats lets us defer the entire replay-import subsystem. Full search stays in v1 by choice — it's the recommendation quality that makes the product worth trusting.

Fast-follows (post-MVP, in order)

  2. LLM explanations — stream "why this pick" via the existing /api/gameplan route; never blocks the recommendation.
  3. Robustness — more resolutions/ultrawide, localized clients, and patch-resilient ROI config that updates without a client release.
  4. Overlay polish — collapse-to-pill between picks, multi-anchor layouts, and per-user placement.
Long pole: vision calibration needs a real Storm League draft capture (ban row + pick timer). The vs-A.I. screen we have lacks both. Earlier that capture arrives, earlier the critical path starts.

What a real draft screen tells us

The live screen (above) directly shapes both the overlay and the vision pipeline:

  • Teams are vertical hex columns — yours (blue) down the left edge, the enemy (red) down the right — not horizontal rows. So the overlay tucks into the dark band beside the centre pick-splash and must never cover either column or the bottom hero pool.
  • Little empty space. The screen is dense, so the overlay stays compact and corner-anchored (collapsing to a pill between picks) rather than a large panel.
  • Fixed OCR targets: the map name is top-centre text (INFERNAL SHRINES); the active pick shows the player's battletag above the hero name in the centre; per-player names sit beside each hex.
  • Portrait ROIs are the hex slots (left/right columns) plus the bottom-centre strip of circular hero icons for the available pool.
  • Caveat: this is a Custom / vs-A.I. lobby (note "Elite A.I." and no ban phase). Ranked Storm League draft adds a ban row and pick-order/timer UI, so we calibrate the ROIs against a real Storm League draft — not this screen.
